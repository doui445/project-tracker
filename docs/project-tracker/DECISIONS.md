# DECISIONS — project-tracker

Why each structural choice, and what was rejected. Append-only. Full
rationale for the pre-2026-08-30 entries lives in the local (gitignored)
`_dev-history/specs/`.

## 2026-08-27 — Tracking files live in `docs/project-tracker/`, not the project root

- **Rejected**: all nine files at the project root — the user found it
  cluttered the root.
- **Rejected**: a hidden `.docs/` — the relevant criterion is *who reads
  these files*. `.git/` / `.claude/` are hidden because nobody opens them;
  `STATUS.md` / `JOURNAL.md` are the opposite, the user opens them directly.
- **Rejected**: files directly under `docs/` — recreates the same defect
  (one folder filling with one tool's output mixed with everything else).
- **Kept at the root**: `README.md` (GitHub only renders a repo homepage from
  a root `README.md`) and `CLAUDE.md` (Claude Code only auto-loads it from the
  root, `./.claude/`, or an ancestor of `cwd` — verified against the docs).
- **Chosen**: `docs/project-tracker/` namespace, mirroring the existing
  `docs/superpowers/{specs,plans}/` convention. Bonus: resolves a
  case-insensitive-filesystem collision by having a single `docs/` total.

## 2026-08-29 — Shipped skill is English; machine values are never translated

- The repo went public, so the shipped prose, comments, messages and
  generated HTML were translated to English.
- **Faithful translation** — no logic or structure change. Small fixes
  allowed but each logged, never silent.
- **Never translated**: frontmatter keys and their enumerated values
  (`active`/`paused`/…, `"non"`, `"adopté"`, `"leger"`, `"superpowers"`),
  standard file names, hook names, tags (`#tracker-sync`) — they are data.

## 2026-08-30 — One unified, hook-regenerated portfolio

- **Rejected**: one `PORTFOLIO.html` per scope root, regenerated by asking
  Claude to run the script (depended on Claude's judgment / memory).
- **Chosen**: a single `PORTFOLIO.html` aggregating every tracked project
  across all scopes, location set once in
  `~/.claude/project-tracker/portfolio.txt` (a folder path; `.html` suffix
  tolerated as an explicit file path), regenerated by a deterministic
  `PostToolUse` hook. Absent config → the hook signals Claude, which asks
  once (same pattern as `reminders_list`). All tracked projects included,
  no `uses_git` filter. Project paths shown as `~/…`, not scope-relative.

## 2026-08-30 — Packaged as a Claude Code plugin, install script kept in parallel

- A standalone skill cannot register hooks, so `install-project-tracker.sh`
  had to hand-edit `~/.claude/settings.json`.
- **Chosen**: repo root = plugin root; add `.claude-plugin/{plugin,marketplace}.json`
  + `hooks/hooks.json`. The skill stays under `skills/project-tracker/`.
- The author dogfoods via a **local-folder marketplace** — tests exactly what
  others receive.
- Install script **kept in parallel** for users who don't want a marketplace.
- The two hooks that hardcoded `$HOME/.claude/skills/project-tracker/...`
  became **self-relative** so they work in all three modes.
- Version kept in sync across `plugin.json` and `marketplace.json`; a test
  enforces it.

## 2026-08-30 — `project:` frontmatter is the folder name, never asked

- One less bootstrap question; removes a class of drift between the frontmatter
  and the actual folder. The portfolio generator keys on it.

## 2026-08-30 — Tracking files are committed, not gitignored

- **Context**: this repo is public and now tracks itself — is `docs/project-tracker/`
  version-controlled or ignored?
- **Chosen**: commit all nine files.
  - They are the project's memory and documentation; `CHANGELOG.md`,
    `DECISIONS.md`, `ROADMAP.md`, `GLOSSARY.md` are standard public artifacts.
  - `README.md` / `CLAUDE.md` must be committed anyway (GitHub homepage,
    Claude Code auto-load).
  - The skill's own "concurrent sessions" safeguard runs
    `git diff -- docs/project-tracker/STATUS.md` before writing — only
    meaningful if the file is tracked.
  - For `project-tracker` specifically, committing them is public dogfooding:
    the output *is* live documentation of what the plugin produces.
- **Rejected**: gitignoring `STATUS.md` / `JOURNAL.md` / `BACKLOG.md` to avoid
  noisy rewrite diffs — that split only makes sense when the content is
  genuinely sensitive for a public repo (unreleased strategy, client names).
  Not the default.
- **Accepted downside**: `STATUS.md` is rewritten every session → churny diffs
  and possible cross-session conflicts; handled by the skill's collision logic.

## 2026-08-30 — Output language: global default + two overrides, catalogue-driven

- **Context**: v0.4.0 makes the output language (EN/FR) selectable. Where does
  the setting live, how deep does localisation go, and how does a language
  change propagate?
- **Chosen**:
  - `~/.claude/project-tracker/language.txt` = machine default; `language:`
    frontmatter key on `STATUS.md` overrides it for one project's tracking
    files; a `language:` line in `portfolio.txt` overrides it for the
    portfolio. Reminders always follow the global. The chat always follows
    the session's conversation language, never a setting.
  - **Full localisation** of the tracking files (headings + template phrases +
    prose), driven by a per-language catalogue
    `skills/project-tracker/references/i18n/<code>.md`. Machine values
    (frontmatter keys/enums, file names, hook names, `#tracker-sync`, the
    codes) are never translated.
  - `generate_portfolio.py` keeps its **own** Python `STRINGS` table — the
    `.md` catalogue is for Claude at runtime, the Python table for the
    generator; both carry a same-keys guard test.
  - A language change on a project with existing content → Claude **proposes a
    full retranslation**, append-only entries included (dates preserved), with
    an autonomous subagent review loop (cap 3, surfaces only judgement calls).
- **Rejected**: a single global setting with no per-project override (a
  bilingual user with FR and EN projects couldn't mix); a per-project-only
  setting (re-asked every bootstrap, and the multi-project portfolio still
  needs one language); freezing a project's language at creation (too rigid);
  hard-coding EN/FR everywhere with no extension path (adding a 3rd language
  would touch every file — the catalogue model makes it "add a file").
- **Accepted downside**: two parity guards to keep in sync (`.md` catalogue +
  Python table) rather than one source; the retranslation of append-only
  files is a sanctioned exception to "never rewrite an append-only file".
- Spec: `_dev-history/specs/2026-08-30-output-language-design.md` (D1–D15).
